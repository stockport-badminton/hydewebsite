# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Server-rendered Express/EJS website for Hyde Badminton Club. No build step, no test suite, no linter configured.

## Commands

- `npm start` — run the server (`node server.js`) on `PORT` env var or 3000.
- `npm run dev` — run with `nodemon` for auto-restart on file changes. Use this while developing.
- There are no test or lint scripts in this repo.

## Architecture

**Entry point:** `server.js` just requires `app.js` and calls `.listen()`. `app.js` itself is now just setup — Express config, static mounts, the Sass compile, mounting four routers, and the global 404 catch-all. Route logic lives in `routes/*.js` (Express Routers), one file per concern: `push.js` (PWA + push notifications, see below), `pages.js` (all Contentful-backed pages), `fixtures.js`, `tables.js`. **The 404 catch-all must stay in `app.js`, mounted after all the routers** — a router-local `router.use(fn)` with no path would intercept requests meant for routers mounted after it, since it matches any path that reaches that router.

**Content sources — three distinct patterns:**
1. **Contentful CMS** — most static pages (`/`, `/how-to-find-us`, `/links`, `/history/:season`, `/gallery`, `/news`, `/contact-us`), handled by `routes/pages.js`, fetch a specific entry by hardcoded Contentful entry ID via the client in `lib/contentful.js`, convert the rich-text field with `documentToHtmlString`, and render it through the generic `views/homepage.ejs` template (which wraps the resulting HTML string in a `.prose`-styled card via `entry`). The Contentful space ID and access token are read from `CONTENTFUL_SPACE`/`CONTENTFUL_TOKEN` env vars (`dotenv`-loaded locally from a gitignored `.env`; see `.env.example`). CI writes `.env` from GitHub Secrets before deploying.
2. **Fixtures, scraped out-of-band** — `scripts/scrape-fixtures.mjs` fetches HTML from `manchesterbadmintonleague.org.uk/fixtures.php` (cheerio) and JSON from `tameside-badminton.co.uk/fixtures/club-Hyde`, normalizes both into a common shape (`team`, `opposition`, `homeOrAway`, `competition`, `result`, `status`, `season`, etc.) and writes `data/fixtures.json`. Manchester and Tameside are different leagues with independent team naming for the same club — Manchester enters Hyde's squads as `Hyde 1`/`Hyde O`, Tameside as `Hyde A`/`Hyde B`/`Hyde C` — so `team` is kept as whichever raw name the source uses rather than merged; there are 5 distinct team pages, not 3. `season` (e.g. `20252026`, an Aug–Jul cutover computed by `lib/season.js`, shared between the CJS app and this ESM script via Node's CJS interop) lets `/fixtures/:team/:season?` show a specific season; omitting `:season` defaults to the current one. The scraper's `archiveAndMerge` never deletes — once a league site drops an old fixture from its live feed (new season started), it stays archived in `data/fixtures.json` permanently, so history accumulates across seasons instead of only ever reflecting the live feed. It runs on a GitHub Actions cron (`.github/workflows/scrape-fixtures.yml`, daily + manual dispatch) which commits the result straight to `main`. `routes/fixtures.js` just fetches that file's raw GitHub URL (via `lib/fixtures-data.js`, shared with `routes/push.js`) (`raw.githubusercontent.com/stockport-badminton/hydewebsite/main/data/fixtures.json`, cached in memory for 10 minutes), filters/formats for the requested team/season, and additionally computes a win/loss/draw badge per row from `homeScore`/`awayScore`/`homeOrAway` — no live scraping happens on the request path anymore, so a markup change on either league site can't crash or 500 a live request; worst case the next scheduled scrape run fails and the site keeps serving the last good data. `deploy.yml` has a `paths-ignore: data/**` so those scrape commits don't trigger an App Engine redeploy. The repo is public specifically so `raw.githubusercontent.com` is fetchable without auth — nothing sensitive is committed (`.env` stays gitignored).

   Manchester publishes dates without start times, so the scraper stamps each Manchester fixture at 19:00 **UTC** via `Date.UTC` (`manchesterDateIso`). It used to use local wall-clock time, so a run on a UK laptop in BST produced different ISO timestamps — and therefore different `id`s — than the UTC CI runner, and `archiveAndMerge` (which dedupes by `id`) archived both copies. `normaliseManchester` repairs any such archived entries on every run (re-stamps at 19:00Z on the fixture's UK calendar date, rebuilds the id, drops duplicates). Treat Manchester's time-of-day as meaningless; only the date is real.

3. **Tables, scraped out-of-band the same way** — `scripts/scrape-tables.mjs` fetches the same two league sites' standings pages and writes `data/tables.json`, one entry per *division Hyde actually has a team in* (not every division either league runs). Both source pages dump every division into one HTML blob with "Division N" (or, on Manchester's page, also `Open Division A`/`Open Division B` — a second heading pattern that's easy to miss and did in fact get missed on the first pass) as in-band row markers rather than separate tables, so the scraper has to track "current division" as it walks rows rather than selecting a table per division. Manchester's Hyde 1/Hyde O and Tameside's Hyde A/B/C can land in the same or different divisions each season (currently Hyde A and Hyde B share Tameside Division 1; Hyde C is alone in Division 2; Hyde 1 and Hyde O are in separate Manchester divisions) — the scraper doesn't hardcode this, it just keeps whichever division table contains a team name matching `isHydeTeam` (`lib/hyde.js`, shared with the fixtures scraper). Manchester's table has far more columns than a visitor needs (aces, penalty/conceded points); only `Pos/Team/Played/Won/Drawn/Lost/Games-per-Match/Total Points` are kept. Tameside's table keeps every column it has (`Team/P/W/L/Avg`) since that's all it publishes. `routes/tables.js` fetches `data/tables.json`'s raw GitHub URL the same way fixtures does (10-minute in-memory cache) and `views/tables.ejs` just renders whatever `columns`/`rows` it's given — no Manchester/Tameside branching logic in the template.
4. **Static/no-op fallback** — the catch-all 404 handler in `app.js` renders `homepage.ejs` with an error message.

**Views (`views/*.ejs`):** `header.ejs` opens `<html>`/`<head>`/`<body>` (fonts, favicon, stylesheet); `nav.ejs` is just the `<nav>` element (sticky, not fixed — no compensating body padding needed); `footer.ejs` closes the page. Each top-level view (`homepage.ejs`, `fixtures.ejs`, `tables.ejs`, `gallery.ejs`) is responsible for its own `<main class="container">...</main>` in between — this used to be split awkwardly across `nav.ejs`/`footer.ejs` with mismatched unclosed `<div>`s that only worked because browsers silently correct invalid HTML; now each file's markup is self-contained and valid. `views/partials/page-header.ejs` renders the wine banner + `<h1>` at the top of every page (pass `pageSubheading` for an optional second line). `homepage.ejs` wraps whatever Contentful HTML it's given in a `.prose`-styled card — that class (in `styles/_components.scss`) is what makes raw rich-text headings/paragraphs/links/tables look right, so routes no longer need to hand-inject Bootstrap classes into the rendered HTML (`routes/pages.js` doesn't do the `replaceAll("<table>", ...)` -style hacks the old inline `app.js` routes did). `fixtures.ejs` and `tables.ejs` wrap their tables in `.data-card` (rounded, wine header row, striped body); `fixtures.ejs` renders a `.badge-result` pill next to each result when `outcome` is set. `gallery.ejs` keeps the original single-image Bootstrap carousel, just restyled.

**Styling:** `styles/main.scss` (imports `_tokens.scss` then Bootstrap then `_components.scss`) is compiled once at process startup (in `app.js`, via the `sass` package/Dart Sass) into `public/style.css`, then served in-memory at `/public/style.css` — `public/` the gitignored on-disk folder from older versions of this setup no longer exists; nothing is written to disk. `_tokens.scss` overrides Bootstrap's own SCSS variables (`$primary`, `$secondary`, `$font-family-sans-serif`, etc. — must be set before Bootstrap's `@import`, since that's how Bootstrap theming works) for the wine/gold "Heritage Club" palette (Fraunces headings, Source Sans 3 body, loaded via Google Fonts `<link>` in `header.ejs`), plus a `:root` block of plain CSS custom properties for values Bootstrap has no slot for (`--accent`, `--win`/`--loss`/`--draw`). `_components.scss` holds all the hand-written component rules (nav, footer, page-header banner, `.prose`, `.data-card`, result badges, carousel). This folder replaced a `bootstrap/style.sass` file that was actually SCSS despite its extension — that old footgun is gone now that the file is honestly named `.scss` and Dart Sass can infer the syntax without an explicit `syntax: 'scss'` option.

**Static assets:** `static/` (custom JS/images) is served at `/static`; the entire `node_modules` tree is also exposed at `/scripts` specifically so `static/js/main.js` can `import` Bootstrap's client-side JS bundle directly from `node_modules/bootstrap/dist/js/bootstrap.bundle.min.js` as an ES module in the browser. There's no real club logo asset — the favicon is a small inline SVG monogram (data URI, in `header.ejs`) rather than an invented image file.

**PWA & push notifications** (ported from the sibling `remnants-badminton` Astro/Netlify site, whose `src/lib/push/README.md` describes the original design):
- `static/sw.js` — service worker, served at **`/sw.js`** by `routes/push.js` (root path so its scope covers the whole site; `/static/sw.js` would only control `/static/*`). Offline caching: pages and same-origin CSS/JS network-first (nothing here is content-hashed), images/fonts stale-while-revalidate, `/offline` fallback. Plus `push`/`notificationclick` handlers. Bump `VERSION` when changing caching logic. Only registered (from `footer.ejs`) when `app.locals.enableServiceWorker` — true on App Engine (`GAE_ENV` is set) or with `ENABLE_SW=1` locally.
- `/manifest.webmanifest` (in `routes/push.js`) + `static/icons/*.png` (rendered from the "H" favicon monogram).
- `/notifications` — opt-in page (`views/notifications.ejs` + `static/js/push-panel.js`). Subscribers pick topics and types (`results`, `reminders`); empty list = everything. `/notifications?team=Hyde A` preselects one team (linked from each fixtures page).
- **Topics** are `"<league>|<team>"` (`Manchester|Hyde 1`, `Tameside|Hyde A` — `lib/push/teams.js`). The page offers the current season's sides; `/push/subscribe` accepts any side ever seen in `data/fixtures.json`. A Hyde-v-Hyde derby is scraped once (under the home side) so `topicKeysOf` adds the other side's key too.
- **Storage**: the project's existing `(default)` database, which is **Firestore in Datastore mode** (App Engine created it in 2023; a project gets one `(default)` database and only that one is in the free tier, so push uses it rather than a separate Native-mode database). Kind `PushSubscription`, key = sha256(endpoint), the subscription JSON stored unindexed — `lib/push/store-datastore.js` (`@google-cloud/datastore`). On App Engine it authenticates as the default service account (`roles/editor`); locally it uses ADC. Overridable with `DATASTORE_PROJECT` / `DATASTORE_DATABASE` / `PUSH_KIND`. Datastore mode has no client-SDK access or security rules — only the server can reach it.
- **Sending**: `scripts/push-notify.mjs` → `POST /push/send` (Bearer `PUSH_SEND_SECRET`) → `lib/push/send.js` (web-push, prunes 404/410 subscriptions). Results: the daily scrape workflow runs it after committing, diffing `data/fixtures.json` HEAD~1→HEAD (`lib/push/results.js`; >10 new results is treated as a back-fill and not sent). Reminders: `.github/workflows/match-day-reminders.yml` runs `--reminders tomorrow` at 18:00 UK and `--reminders tonight` at 17:00 UK (`lib/push/reminders.js`, matches on UK calendar date); it fires at three UTC hours and picks the UK slot from `github.event.schedule`, so GMT/BST is handled.
- Shared libs in `lib/push/` are CommonJS so both the app and the ESM script can load them (same pattern as `lib/season.js`). The VAPID public key is in `lib/push/config.js`; rotating the pair invalidates every subscription.
- Secrets: `VAPID_PRIVATE_KEY` + `PUSH_SEND_SECRET` in GitHub secrets (written into `.env` by `deploy.yml`; `PUSH_SEND_SECRET` is also used by the scrape and reminder workflows). Optional `SITE_URL` repo variable (default `https://www.hydebadminton.co.uk`).
- Testing: `node scripts/push-notify.mjs --dry-run` (or `--base HEAD~20 --dry-run`), `--reminders tomorrow --date 2026-11-17 --dry-run`, `PUSH_SEND_SECRET=… node scripts/push-notify.mjs --test "Hello"` (sends to every subscriber) — or, without the secret locally, run the "Match Reminders" workflow manually with kind `test` (GitHub can't show a secret once saved). Push needs HTTPS (or localhost); on iOS only from the Home Screen app (16.4+).

**Deployment:** Google App Engine Standard, project `stockport-badmin-1531321435304`, region `europe-west2`, custom domain `hydebadminton.co.uk`/`www.hydebadminton.co.uk` mapped directly onto the App Engine app (independent of how deploys happen). `runtime:` in `app.yaml` must track a currently-GA Node runtime — App Engine Standard rejects deploys on end-of-support runtimes outright (this broke deploys once when `nodejs20` aged out; check `gcloud app runtimes list --environment=standard` before bumping). `.gcloudignore` excludes `node_modules` and git metadata from deploys, but does NOT exclude `.env` — `gcloud app deploy` uploads whatever's in the working directory, so the CI-generated `.env` (see below) rides along intentionally.

**CI/CD:** GitHub Actions (`.github/workflows/deploy.yml`) deploys to App Engine on every push to `main`. Auth uses Workload Identity Federation (no service-account key) via the `github-deployer` service account, scoped to the `stockport-badminton/hydewebsite` repo specifically. The workflow writes `CONTENTFUL_SPACE`/`CONTENTFUL_TOKEN`/`VAPID_PRIVATE_KEY`/`PUSH_SEND_SECRET` from repo secrets into a `.env` file immediately before `gcloud app deploy`, since App Engine Standard has no other first-class way to inject secrets that isn't itself committed to the repo.
